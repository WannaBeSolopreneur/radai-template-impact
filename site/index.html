Problem

A team selling radiology AI has to see, in one glance, whether bookings, pipeline, and customer use are keeping up with the quarter.

Solution

Each tile compares a live number with its goal. The actions are written from those same tables, so the page and the warehouse agree.

    How it's built

    The tiles and the action list are columns in the warehouse. This page only reads them.

    Path

    1. Generator Python in rad_model. Seed 20261103. behavior.yml for studies. commercial.yml for accounts, deals, spend, and goals.
    2. Raw tables DuckDB schema raw. studies, customers, accounts, opportunities, marketing_spend, goals, quarter, generation_meta.
    3. Staging dbt views. Latest ingest wins. Blank modality is filled. A short clock skew is repaired.
    4. Intermediate int_studies adds clocks and period. int_opportunities ranks the stage from lead to won.
    5. Marts Facts, dims, and the goal marts. Study facts keep one customer and drop fixtures.
    6. Semantic layer dbt/models/semantic.yml. 7 semantic models and 23 metrics. Day time spine on metric_time_spine.
    7. Site and BI rad_model/export_site.py writes site/data.js. The README maps the same marts to an Omni topic. Hex is not wired here.

    Semantic metrics

    These are the metrics in semantic.yml that feed the dashboard. None of them set a filter. The window lives in the model.

    quarter_bookings

    simple · measure quarter_bookings_arr

    Closed-won ARR since the quarter started.

    quarter_new_logo_count

    simple · measure quarter_new_logos

    First-time customers closed since the quarter started.

    quarter_marketing_pipeline

    simple · measure quarter_marketing_pipeline_arr

    Marketing-sourced ARR that reached a meeting this quarter. Outbound is not in the measure.

    cost_per_opportunity

    ratio · channel_spend / channel_opportunities

    Channel spend divided by opportunities that reached a meeting.

    segment_win_rate

    ratio · won_deals_metric / closed_deals_metric

    Closed-won deals divided by closed-won and closed-lost deals.

    ai_impression_acceptance_rate

    ratio · ai_accepted_count / ai_scored_count

    Accepted impressions divided by accepted, edited, and rejected. This is not the adoption goal.

    case_mix_adjusted_time_on_report_change

    simple · measure adjusted_report_change_minutes

    Mix-adjusted change in time on the report. Negative means faster.

    median_report_turnaround

    simple · measure median_turnaround_minutes

    Median minutes from exam completed to signed.

    Pipeline coverage, net revenue retention, portfolio AI adoption, and minutes saved are not semantic metrics. They are formulas in mart_goal_status, because each one joins more than one table.

    yaml · dbt/models/semantic.yml

    - name: cost_per_opportunity
  label: Cost per opportunity
  type: ratio
  type_params:
    numerator: channel_spend
    denominator: channel_opportunities

- name: segment_win_rate
  label: Win rate by segment
  type: ratio
  type_params:
    numerator: won_deals_metric
    denominator: closed_deals_metric

    sql · mart_goal_status.sql · pipeline coverage

    open_pipeline.open_arr * 1.0 / nullif(
    (select target_value from {{ ref('stg_goals') }} where goal_id = 'bookings')
    - bookings.bookings_arr,
    0
)

    sql · mart_goal_status.sql · net revenue retention

    select sum(arr) * 1.0 / sum(arr_one_year_ago) as nrr
from {{ ref('stg_accounts') }}
where arr_one_year_ago > 0

    sql · mart_goal_status.sql · portfolio AI adoption

    sum(ai_used) * 1.0 / count(*) as adoption
from {{ ref('fct_portfolio_studies') }}

    Goal status

    On track

    Pace goals at 95% of a straight-line pace or better. Snapshot goals at 95% of the full target or better.

    At risk

    From 80% up to the on-track line.

    Behind

    Below 80%.

    Pace uses days elapsed over days in the quarter. This snapshot is day 33 of 92. The 0.95 and 0.80 cutoffs are columns on raw.quarter, not constants in the page.

    sql · mart_goal_status.sql

    case
    when goals.metric_kind = 'pace'
        and actuals.current_value
            >= goals.target_value
            * calendar.days_elapsed * 1.0 / calendar.days_in_quarter
            * calendar.on_track_ratio
        then 'on_track'
    when goals.metric_kind = 'pace'
        and actuals.current_value
            >= goals.target_value
            * calendar.days_elapsed * 1.0 / calendar.days_in_quarter
            * calendar.at_risk_ratio
        then 'at_risk'
    when goals.metric_kind = 'pace' then 'behind'
    when actuals.current_value >= goals.target_value * calendar.on_track_ratio
        then 'on_track'
    when actuals.current_value >= goals.target_value * calendar.at_risk_ratio
        then 'at_risk'
    else 'behind'
end as status

    One customer at a time

    Study marts keep the customer in var customer_id, which defaults to cust_northbay. Test fixtures are dropped in the same predicate. assert_customer_isolation fails if any other customer lands in those marts. Redcedar stays in int_studies so the test has something to keep out.

    sql · fct_studies.sql

    from {{ ref('int_studies') }}
where customer_id = '{{ var("customer_id") }}'
    and is_test_fixture = 0

    The Snowflake row access policy below is an example in dbt/analyses. dbt does not execute it on DuckDB. A customer role sees one customer_id. The internal role RAD_INTERNAL_ANALYTICS sees every customer.

    sql · dbt/analyses/snowflake_row_access_policies.sql

    create or replace row access policy governance.rad_customer_isolation
as (customer_id varchar) returns boolean ->
    is_role_in_session('RAD_INTERNAL_ANALYTICS')
    or exists (
        select 1
        from governance.role_customer_access as access
        where access.role_name = current_role()
          and access.customer_id = customer_id
    );

There is no site build step. Chart.js is vendored under site/vendor. The folder is plain static files, which is what GitHub Pages serves.
